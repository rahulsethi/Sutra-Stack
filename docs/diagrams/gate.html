The Gate — four independent enforcement points

Every read path in the product passes all four. They are deliberately redundant: each one has failed independently in the system Sutra was extracted from, and the other three held. The ceiling is read from the environment at server startup and is never accepted as a tool argument — a model can ask for anything, and cannot change what it is allowed to see.

Why four, and not one

  • Defence in depth is not redundancy here.
  • Each of the four has failed independently in the upstream system's history — a dead path-floor band, an unmatched key shape, a stale index, a config a harness stopped reading.
  • Each time, the other three held.

What cannot lift the floor

  • A promotion — Brain.visible() only consults them for private.
  • An override — the MCP path passes allowSecret: false, unconditionally.
  • A ceiling — local_only fails the guard at every ceiling but its own.
  • An Enterprise role — the floor is checked before clearance is read.

The trust demo

  • sutra gate reports the ceiling, what is visible, and what is withheld by tier.
  • It computes those counts with the same visible() the real read paths use — not a separate summary that could drift from them.
